# Murder Mystery Game
## Video Demo: <https://youtu.be/DCZ0JbUE4MY>
## Description
### Premise
The project I created for this course’s final is an interactive murder mystery game, inspired by both Clue and Murdle. The user is given three suspects, three possible murder weapons, and three possible locations for the murder, and to win the game, they must figure out which suspect, weapon, and location was involved in the murder. The game takes form as a mostly text-based adventure on this website. I made this game because it combines computer science with my interests of both text-based adventures and puzzles.
### Gameplay
After starting the game by clicking on this arrow, the user progresses linearly through the opening information, including the game’s instructions and all the suspects, weapons, and locations involved. Then, they can choose which room to “enter”, bringing them to a subpage specific to that room. The first two options are specific to that location and, if chosen, may give the user a clue that will help them solve the murder mystery. After reading the clue, the game tells them they’re still in the room and the same four options are displayed again. The third option is to move to another location; upon choosing which location they want to move to, the user will be given another, almost identical quartet of options, except with the first two options specific to that location. Finally, the fourth option is for when the user wants to make their final accusation. Once this option is selected the user is prompted to enter the suspect, weapon, and location they believe was involved with the murder, each on a separate page. If the user guesses incorrectly, they’re brought to a losing screen, and if they choose correctly, they’re brought to a winning screen. The user can navigate back to the start of the game from there.
### Challenges
One challenge I faced was how to shuffle lists, which turned out to be easy but took me a while to figure out. Another layer to this challenge was that I had to shuffle two lists the exact same way, so that possible_suspects[i] and possible_suspects_clues[i] would pair up before and after shuffling, with a different value for i of course. I solved this problem by using Python’s built-in zip() function, which combined the elements of both lists into tuples while I shuffled them.
Of course coding the actual game was challenging as well – such as figuring out how to get the user to keep looking around until they wanted to make their final accusation, which I solved using a while loop – but these challenges were minor and had simple solutions that I figured out quickly (such as in the example above.)
### Frontend Design Choices
I had always planned for this murder mystery game to take form as a simple text-based adventure website, though the colors, font, and layout of each page I had to spend more time on. Between a brown background with black text (to look more old-timey) and a red/maroon background with white text, I chose the latter, because it matched the theme of the game better. I decided that Playfair Display was a better font than any modern ones because, again, I wanted the game to have an older atmosphere. I also wanted my game to have some “special features” so it wasn’t just a plain old text-based adventure game. One of these features was the use of images on the page detailing the suspects, weapons, and locations the user would encounter. The other was having each option zoom in if the user hovered over them. And of course, I designed my website to be responsive to different screen sizes as well.
### Backend Design Choices
Originally, the information for each location – its name, description, options, and clues – were going to be stored in a list or dictionary. However, I decided a database (which I would access using SQL) would be a more efficient way of storing this information, especially since I was designing one page for all the locations and having an id for each location would help me determine what values I should pass in for the location’s name, description, etc. to the html file. Another major backend decision I made was to use buttons, not links, for each clickable option part of the game. The reason for this was so I could keep them in a form and submit that form via POST, which made figuring out what option the user clicked a lot easier.
### Files
There are a good number of html files for this project, starting with layout.html, which contains the overall layout of each page along with links to Bootstrap and styles.css. Next are the html files for each page: homepage.html for what the user sees as they open the game; instruction.html for the instructions page; swl.html for the page detailing the suspects, weapons, and locations; entered.html for telling the user they’ve entered the mansion (started the game); location-change.html to allow the user to change their location through a form submitted via POST; location.html, containing info for each location and what the user could do there, in a form of options submitted via POST; accuse-suspect.html, accuse-weapon.html, and accuse-location.html for the user’s final accusation, where they can choose which suspect, weapon, and location they think was involved through a form submitted via POST; and finally, loser.html and winner.html, the losing and winning screens respectively. Other files involved in the program include app.py (the backend) and styles.css (the stylesheet for all html pages.)
### Languages, Frameworks, etc. Used
I used Figma to design my website, then coded the frontend using HTML, Bootstrap, and CSS; the backend was coded using Python, Flask, and SQL.
